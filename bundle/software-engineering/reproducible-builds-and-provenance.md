# Make the build an inspectable transformation

A software build transforms source, dependencies, tools, configuration, and
environment into one or more artifacts. Reproducibility means that repeating
the build with the same relevant inputs produces bit-for-bit identical output;
it is stronger than merely recording a version number. Work toward explicit,
resolved inputs, deterministic tooling, isolated environments, controlled
timestamps and ordering, and a documented build procedure. When exact
reproduction is impractical, document the limitation and preserve the best
available evidence.

SLSA defines provenance as verifiable information describing where, when, and
how an artifact was produced. Its current build requirements call for
provenance that identifies the output package by cryptographic digest and
describes its production.[^slsa-build-requirements] Provenance is useful only
when it is generated by a trustworthy process and consumers compare it with
their expectations.

# Verify what was shipped

Record the source revision, build definition, resolved dependencies, builder,
parameters, artifact digests, and relevant environment details. Sign or
otherwise authenticate provenance when the threat model requires it. Verify
that the artifact digest matches, the source and builder are expected, and the
build parameters and dependencies are acceptable. Do not infer that a
reproducible artifact is automatically secure: reproducibility does not cover
all source, dependency, builder, or distribution threats.[^slsa-provenance]
